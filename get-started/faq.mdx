Short answers to the questions customers actually hit, each linking to the full page. If your question isn't here, [support](mailto:support@changeguard.ai) would rather you ask than guess.

## Connecting

<AccordionGroup>
  <Accordion title="What do I need to install in my Kubernetes clusters to use ChangeGuard AI?">
    For standard Kubernetes API-state evidence, **nothing**. ChangeGuard Fleet connects centrally using customer-authorized, read-only access — see [Connect your EKS fleet](/get-started/connect-your-fleet). ChangeGuard Edge is an optional in-cluster install for signals that genuinely require local presence (runtime detection, node benchmarks) or environments Fleet cannot reach centrally.
  </Accordion>

  <Accordion title="Does connecting AWS give ChangeGuard AI access to all my clusters?">
    No. The AWS connection authorizes **discovery** — listing and describing your EKS clusters with a role you create. Kubernetes read access is a separate, per-cluster grant you make explicitly through the generated authorization workflow, and you can revoke it per cluster at any time. See [Connect your EKS fleet](/get-started/connect-your-fleet).
  </Accordion>

  <Accordion title="Where do I see whether an environment is healthy?">
    **Environments → Connected environments** shows every environment with its status, evidence source (Fleet, Edge or both), judgment readiness, execution readiness, latest Permit and mode. **Environments → AWS Account Center** shows each connected AWS account and whether that connection is healthy, with one guided action per problem. See [Connected Environments](/connect/connected-environments) and [AWS Account Center](/connect/aws-account-center).
  </Accordion>

  <Accordion title="Does enabling execution give ChangeGuard AI write access to my cluster?">
    Only through a separate, per-environment identity that you create and can revoke: a role in your account with no AWS permissions, mapped to a Kubernetes group that holds `get`, `list` and `patch` on workloads in exactly the namespaces you chose — and even that identity does nothing without a short-lived, single-use [Permit](/govern/permit) for one approved change. Enabling execution approves nothing. See [Enable execution](/start-here/enable-remediation).
  </Accordion>

  <Accordion title="Do I need to install Edge for ChangeGuard AI to apply fixes?">
    No. The **Cloud Executor** acts on a reachable EKS cluster with nothing installed. Edge is an optional evidence collector; it never acts, and it is not a prerequisite for execution or for Auto. A **Local Executor** exists for topologies or policies that require local presence. See [Fleet, Edge and the Executor](/connect/fleet-edge-executor).
  </Accordion>

  <Accordion title="Our clusters sit behind an egress proxy — does Fleet still work?">
    Fleet reverses the direction: ChangeGuard AI connects _to_ your Kubernetes API endpoint centrally, so the cluster itself needs no outbound path to ChangeGuard AI for standard evidence. The direct-egress requirement below applies only to the optional Edge install.
  </Accordion>
</AccordionGroup>

## Installing ChangeGuard Edge (optional)

<AccordionGroup>
  <Accordion title="The install command exits immediately with an error about CG_CLUSTER_NAME">
    Both `CG_API_KEY` and `CG_CLUSTER_NAME` are **required** — the installer refuses to run without them, and the Helm chart refuses to render without `agent.clusterName`. The correct commands are on [Install ChangeGuard AI](/get-started/install).
  </Accordion>

  <Accordion title="How long until I see my first score?">
    Your cluster connects within about a minute of install (up to ~2 minutes on a first-ever install while images pull), and the first CSC Score follows within ~10 seconds of connecting. If it's been longer, the [fix table](/get-started/connect-first-cluster#if-a-step-didnt-produce-the-result-shown) covers the three causes — it's almost always egress or the API key.
  </Accordion>

  <Accordion title="We use an HTTP(S) proxy — can the collector go through it?">
    Not today. The cluster needs **direct outbound HTTPS** to `api.changeguard.ai:443`. This is tracked on [Known Limitations & Roadmap](/concepts/limitations-and-roadmap).
  </Accordion>

  <Accordion title="Can we install air-gapped or from our own registry?">
    Yes — mirror the images and repoint every one of them with `--set global.imageRegistry=<your-registry>`. The registry list is on [Before you install](/get-started/before-you-install).
  </Accordion>

  <Accordion title="Does anything run privileged?">
    One component: the **Falco DaemonSet** (runtime syscall detection), on by default with security scanning. Everything else runs unprivileged and read-only. What it mounts, why, and how to disable it: [Permissions & RBAC](/get-started/permissions#security-scanners-optional-on-by-default).
  </Accordion>

  <Accordion title="How do I uninstall completely?">
    Helm uninstall plus one manual step (deleting the CRD) — exact commands on [Install ChangeGuard AI](/get-started/install#uninstall--rollback). Removing already-sent data is per-cluster in-app; full-tenant erasure goes through support.
  </Accordion>
</AccordionGroup>

## Using ChangeGuard AI

<AccordionGroup>
  <Accordion title="What do SHIP / HOLD / BLOCK mean?">
    The one verdict vocabulary, everywhere: **SHIP** = sufficient evidence supports proceeding. **HOLD** = ChangeGuard AI cannot establish that proceeding is safe enough — including when important evidence is missing or too stale to trust (it says so rather than pretending the evidence is available). **BLOCK** = affirmative evidence indicates the change should not proceed. A verdict is a judgment, not an authorization: it grants nothing and, in the product, blocks nothing. In CI, the shipped templates fail the job on BLOCK by default and never on HOLD — see [Use the Verdict in CI](/gate-your-pipeline).
  </Accordion>

  <Accordion title="The dashboard says my score is unavailable or shows a red zero">
    A real score of 0 renders as a red 0/100; “Calculating your first score” means the first snapshot hasn't arrived yet. If it turns into “Score unavailable,” the collector isn't pushing — use Retry and the [connection checks](/get-started/connect-first-cluster).
  </Accordion>

  <Accordion title="I don't see the Engineering Advisor / Opinion / Experience">
    Expected — those are **Early Access**, off by default, and not self-serve. What's GA for every tenant and how to join EA: [Engineering Advisor](/get-started/engineering-advisor) and [Product concepts](/concepts/overview#early-access).
  </Accordion>

  <Accordion title="How do I change the collector's CPU/memory?">
    Defaults are requests 25m/64Mi, limits 500m/512Mi (chart ≥ 5.3.6). Override any subset: `--set agent.collector.resources.limits.memory=1Gi` — see [Operations](/operations/overview#scaling--footprint).
  </Accordion>

  <Accordion title="How do I rotate an API key safely?">
    Create the new key in-app, update the `changeguard-credentials` Secret, restart the collector, then revoke the old key — steps on [Operations](/operations/overview#api-key-handling). There's no self-serve rotation API yet; after a suspected exposure, also confirm invalidation with [support](mailto:support@changeguard.ai).
  </Accordion>

  <Accordion title="Is ChangeGuard AI going to block my deploys?">
    Only where you ask it to. A verdict authorizes nothing, and a judgment in the product blocks nothing. In CI, the shipped templates fail the job on BLOCK by default and never on HOLD; set `enforce_block: false` to run purely advisory. Execution is the other direction — ChangeGuard AI _applying_ a fix — and that happens only in environments where you enabled an Executor, under a Permit, after a person approves (**Advise**, the default) or your policy allows (**Auto**). See [Advise and Auto](/autonomy/autonomy-model) and [ChangeGuard Permit](/govern/permit).
  </Accordion>
</AccordionGroup>

## Troubleshooting

The two canonical fix tables:

- **Install and first connection** — [Connect your first cluster](/get-started/connect-first-cluster#if-a-step-didnt-produce-the-result-shown): repeated `401`s, egress timeouts, an environment never reaching **Ready** in Connected environments, operator `CrashLoopBackOff`.
- **Day-2 operations** — [Operations handbook](/operations/overview#troubleshooting-quick-reference): collector crash loops, stale clusters, missing features, version skew.

Still stuck? [support@changeguard.ai](mailto:support@changeguard.ai) — include the collector logs (`kubectl logs -n changeguard-agent deploy/changeguard-collector --tail=50`); they contain no secrets.
