ChangeGuard AI returns a judgment; your pipeline decides what to do with it. One API call before deploy sends the change you are about to apply and returns a verdict — `SHIP`, `HOLD`, or `BLOCK` — with the readiness score and the reasons, judged against live evidence from the cluster it lands on. Whether a verdict fails the job is your policy, not ours — the examples below show how to wire it up if that is what you want.

<Info>
  Everything on this page uses `POST /api/cicd/preflight`. You need an API key with CI scope — create one in **Settings → API Keys**. (The key issued at signup is agent-scoped and will not work here.)
</Info>

## The verdicts

- **SHIP** — the change was verified against current evidence and nothing critical stands in its way.
- **HOLD** — ChangeGuard cannot verify this change: the target cluster has no current evidence (not connected, or evidence has gone stale). Missing evidence is never treated as safe.
- **BLOCK** — the change was verified and something critical is affirmatively wrong: it exceeds the namespace quota, contradicts the workload's live state, or carries critical findings.

The strictest gate is `verdict == "SHIP"`; teams that only want hard stops can test for `BLOCK` instead. Both are shown below.

## The request

Send the manifest you are about to apply, the cluster it targets, and your own change identifier (a commit SHA works well). The response carries `verdict`, `csc` (readiness score), `reasons` (why, in plain language), `environment_evidence` (`present` or `absent`), and a `verdict_id` you can use to report the outcome later. The full schema is in the [OpenAPI spec](https://api.changeguard.ai/api/openapi-judgment.yaml).

## GitHub Actions

```yaml
- name: ChangeGuard AI Safety Check
  run: |
    RESULT=$(jq -n \
      --arg cluster "production" \
      --arg change  "${{ github.sha }}" \
      --rawfile manifest k8s/deploy.yaml \
      '{cluster_id:$cluster, change_id:$change, change:{manifest:$manifest}}' |
      curl -s -X POST https://api.changeguard.ai/api/cicd/preflight \
        -H "X-API-Key: ${{ secrets.CHANGEGUARD_KEY }}" \
        -H "Content-Type: application/json" \
        --data @-)
    VERDICT=$(echo "$RESULT" | jq -r '.verdict')
    SCORE=$(echo "$RESULT" | jq -r '.csc')
    echo "Verdict: $VERDICT — readiness $SCORE/100"
    echo "$RESULT" | jq -r '.reasons[]'
    if [ "$VERDICT" != "SHIP" ]; then
      echo "::error::$VERDICT — stopped by your pipeline policy (readiness $SCORE/100)"
      exit 1
    fi
```

To stop only on `BLOCK` and let `HOLD` pass as advisory, change the test to `[ "$VERDICT" = "BLOCK" ]`.

## GitLab CI

The same call as a job — add it as the last stage before your deploy job and make the deploy job depend on it:

```yaml
changeguard-check:
  stage: pre-deploy
  image: alpine:3
  before_script:
    - apk add --no-cache curl jq
  script:
    - |
      RESULT=$(jq -n \
        --arg cluster "production" \
        --arg change  "$CI_COMMIT_SHA" \
        --rawfile manifest k8s/deploy.yaml \
        '{cluster_id:$cluster, change_id:$change, change:{manifest:$manifest}}' |
        curl -s -X POST https://api.changeguard.ai/api/cicd/preflight \
          -H "X-API-Key: ${CHANGEGUARD_KEY}" \
          -H "Content-Type: application/json" \
          --data @-)
      VERDICT=$(echo "$RESULT" | jq -r '.verdict')
      echo "Verdict: $VERDICT — readiness $(echo "$RESULT" | jq -r '.csc')/100"
      echo "$RESULT" | jq -r '.reasons[]'
      test "$VERDICT" = "SHIP"
```

## GitOps (ArgoCD, Flux)

Run the gate where the manifest lives: in the pipeline that produces the commit ArgoCD or Flux will sync. The judged change and the applied change are then the same file, and a `BLOCK` stops the merge before the desired state ever changes. The GitHub Actions and GitLab examples above drop into that pipeline unchanged.

## Close the loop

After the deploy, tell ChangeGuard what actually happened. The verdict's record then ends in truth — and readiness learns from real outcomes instead of assumptions:

```bash
curl -s -X POST https://api.changeguard.ai/api/cicd/outcome \
  -H "X-API-Key: $CHANGEGUARD_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"verdict_id\":\"$VERDICT_ID\",\"cluster_id\":\"production\",\"outcome\":\"success\"}"
```

`outcome` is one of `success`, `incident`, `rollback`, or `degraded`.

## Any other CI

The check is one `curl` — it runs anywhere a shell does. POST the manifest to `/api/cicd/preflight`, read `.verdict` and `.csc` from the response, and decide what your pipeline does with them.

<Note>
  **ChangeGuard AI is advisory.** It returns a verdict and the reasons behind it; it has no ability to stop your pipeline on its own. Enforcement is a choice you make in your own CI configuration, and you can change it at any time without changing anything in ChangeGuard AI.
</Note>

<Note>
  Existing integrations built on the older `/api/validate` endpoint keep working — see the [validate reference](/api-reference/validate). That endpoint is advisory-shaped (`SAFE`/`WARN`) and never returns `BLOCK`; new pipelines should gate on `/api/cicd/preflight` as shown here.
</Note>

## What your team sees

A held deploy isn't a mystery. The dashboard shows the verdict, the score at the moment of the check, and the exact factors that drove it — the quota the change would exceed, the live state it contradicts, the evidence that was missing. Fix the finding, re-run the job, ship.
